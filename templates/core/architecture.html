Software architecture

How the pieces of this system fit together. Solid arrows are automatic data flows; the dashed arrow is a manual step by a person (the bank offers no API we may use).

Frontend details

  • {% icon "check-circle" %}Django templates render every page on the server, so pages load fast on branch computers.
  • {% icon "check-circle" %}Vanilla JavaScript (no build step) for the progress bar, the offline receipt queue and notifications.
  • {% icon "check-circle" %}Service worker caches the Teller form so receipts can be captured while the central computer is off.
  • {% icon "check-circle" %}One CSS file with design tokens; WCAG 2.2 AA colours, labels, focus and error handling.

Backend details

  • {% icon "check-circle" %}Python 3.12 and Django 5.2 LTS: ORM, authentication, CSRF and sessions built in.
  • {% icon "check-circle" %}Matching engine: deterministic rules plus RapidFuzz for typo tolerance (no machine learning decides).
  • {% icon "check-circle" %}Statement parser reads CSV or XLSX; header on row 4, rows 1 and 3 ignored.
  • {% icon "check-circle" %}Background thread processes uploads and reports progress; Redis + RQ is the planned upgrade path.

Resource details

  • {% icon "check-circle" %}SQLite for zero-setup local use; PostgreSQL for production (same schema through Django migrations).
  • {% icon "check-circle" %}Append-only audit log: updates and deletes are blocked in code.
  • {% icon "check-circle" %}Local memory cache for sign-in throttling; no external service needed.
  • {% icon "check-circle" %}Optional SMTP e-mail digest; no WhatsApp or Microsoft products are involved.

Constraints that shaped it

  • {% icon "check-circle" %}No direct bank API: Finance downloads the statement manually and uploads it.
  • {% icon "check-circle" %}Central computer is off at night: Tellers queue receipts in the browser and sync later.
  • {% icon "check-circle" %}Zero-cost dependencies: only open-source libraries, no paid services.
